### Findings

[WARN] Local branch `pre-scrub` (tip 7fe3a5f). The unscrubbed history is still in the repository, one command away from the public remote. Requires the operator's action; not a /codefix item.
  Attack vector: No adversary; the risk is accidental publication. `origin` is github.com/peterzat/KX3-Rig, which `gh repo view` reports as PUBLIC and empty. `git push --all origin`, `git push --mirror origin`, or `git push origin pre-scrub` sends the seven commits that exist only on `pre-scrub`. That publishes the station callsign (which resolves to the licensee's name and mailing address through the public FCC ULS database) and the 6-character grid (an area of about 6 km by 5 km), the values the scrub removed from `main`. Once pushed, clones, forks, and GitHub's cached views keep them even after the branch is deleted. A plain `git push -u origin main` does not send them: `push.default` is unset (so `simple`), no push refspec or mirror is configured, and there are no tags, notes, or replace refs.
  Evidence: `git rev-list --count pre-scrub ^main` is 7. At the `pre-scrub` tip the callsign is on 60 lines: tests/test_config.py (2), tests/test_ft8_engine_parts.py (11), tests/test_ft8_messages.py (15), and tests/test_ft8_sequencer.py (32). The 6-character grid is on 2 lines of tests/test_ft8_engine_parts.py. The first five `pre-scrub` commits also set both values as the defaults in kx3rig/config.py. The last four carry the original screenshots, unchanged since the prior scan, which found that the FT8 ones show the callsign and a distance and bearing computed from the real grid. The same search over all eight commits on `main` finds neither value. Its one partial match is the 4-character grid of a demo station (kx3rig/ft8/__init__.py:34).
  Remediation: Push only `main` (`git push -u origin main`). To keep the old history, write it to a bundle outside the repository (`git bundle create ~/kx3-rig-pre-scrub.bundle pre-scrub`), then delete the branch (`git branch -D pre-scrub`). Optionally, once the bundle is verified, `git reflog expire --expire=now --all && git gc --prune=now` drops the unreachable objects. That also removes the local recovery path.

[NOTE] kx3rig/radio.py:245-252, 493-494, and 546-554, kx3rig/controller.py:104 and 201-215. The key-down check refuses while a tuning change is queued or being applied, and (since the cycle 2 fix) while SPLIT or XIT is on. It does not confirm that the state the caller checked is the radio's current state, so narrow windows remain. Re-checked in the cycle 2 post-fix pass: still present, now extended to the SPLIT/XIT refusal and a reconnect window. Confidence: high that each window exists (each was reproduced against the emulator); low that any occurs in normal operation.
  Attack vector: No adversary; all are timing windows. First, a stale main-loop copy. The check reads `Station.radio`, which reaches the main loop through `GLib.idle_add` (controller.py:104) at idle priority. The FT8 engine's 100 ms tick is a default-priority timeout that runs `check_tx()` and then `play_data()` (ft8/engine.py:280-300), so GLib dispatches it ahead of a pending state update. If the link thread finishes applying a tune before that update runs, `tuning_pending` is already False and the check sees the old frequency. The 2 s audio-device scan blocks the main loop (controller.py:372-375, devices.py:149-177; about 18 ms per call on this host), which is longer than the radio's typical reply time of under 10 ms (docs/references.md:27). The Radio view can retune, change band, or change mode during an active FT8 contact: `tune_to`, `select_band`, and `select_mode` check only `Station.transmitting` (controller.py:172-186), and only the FT8 view's band selector checks `engine.busy` (ui/ft8_page.py:292-296). The SPLIT/XIT refusal (controller.py:212-214) has the same limit from the radio's side: a SPLIT or XIT change made on the radio reaches `Station.radio` only at the next IF poll, roughly every 0.2 to 0.3 s in receive (radio.py:520-538). An automatic FT8 key-down in that interval sends one message on VFO B or at the XIT offset; the next one is refused. Second, an unconfirmed readback. `_tuning` clears when `_apply_changes` returns, whether or not the readback confirmed the change. If the FA readback is `?;` (busy or not allowed now, docs/references.md:26-27) or times out, the state keeps the optimistic frequency until a later IF or FA reply (radio.py:566-570). If the radio did not apply the SET, `ptt(True)` succeeds while the radio is still on its previous frequency. Once keyed, the link polls only TQ, PO, and SW (radio.py:506-519), so nothing corrects the frequency during the transmission. Third, a reconnect. A lost port or a radio that stops answering leaves the previous frequency, mode, SPLIT, and XIT in the state, and `_handshake` publishes CONNECTED (radio.py:493) before it reads IF (radio.py:494). Until that reply is dispatched (typically under 10 ms), `can_transmit` approves against the pre-outage values. No handler halts the FT8 engine on a link drop (ui/window.py:175-179), so a contact stays active through an outage between its transmissions. Its next key-down would have to fall inside this window, so this is the least likely of the three.
  Evidence: Demo mode, General class, 14.074 MHz DATA, `tune_to(14_230_000)` with the main loop not iterated. After the emulator applied the tune, `can_transmit(Mode.DATA, 1500, 1550)` and `play_data` were both allowed against the stale 14.074 MHz, and the radio was keyed on 14.230 MHz DATA, which `tx_check` refuses for General. Second run: an emulator that drops the FA SET and answers `?;`, with the link thread held at its next IF poll. `tuning_pending` was False, `state.frequency` read 14.230 MHz, `ptt(True)` returned True, and the radio was keyed on 14.074 MHz. The fix's test (tests/test_radio.py:245-260) compares against `link.state`, not the `Station.radio` copy that the real check reads. Third run (cycle 2 pass): the emulator stopped answering, SPLIT and XIT were turned on, and it answered again. The link published CONNECTED with SPLIT and XIT still off, then the IF-derived state with both on 0.1 ms later.
  Remediation: Have `play_data` and `start_talking` pass the checked frequency and mode to `ptt(True)`. In the link, refuse unless no tuning change is pending and the last confirmed readback (an FA or IF reply dispatched after the most recent SET) matches them. Treat a `?;` or missing post-SET readback as unconfirmed, so key-down stays refused until an IF poll confirms the frequency. Include SPLIT and XIT in that confirmation, ideally from an IF reply the link reads just before it asserts RTS. Publish CONNECTED in the same state update as the first IF reply.

[NOTE] pyproject.toml:11, kx3rig/app.py:164 and 170, data/com.zatloukal.KX3Rig.metainfo.xml:9. The author's full name is published as attribution. The prior personal-data WARN included it, and the scrub kept it, apparently on purpose. Confidence: high that it is intentional.
  Attack vector: No adversary. The first push publishes the name in the package metadata, in the About dialog (developer name and copyright line), and in the AppStream developer entry. The surname and GitHub username also appear in the reverse-DNS app ID `com.zatloukal.KX3Rig` and the `peterzat` repository URLs, and commit author metadata carries the same identity. Removing these four strings alone would not keep the name out of the public repository.
  Evidence: `git grep -i 'Peter Zatloukal' main` returns exactly these four lines. The scrub that produced `main` replaced the callsign and grid in the tests and screenshots but left these lines unchanged.
  Remediation: If the attribution is intended, record it under Accepted Risks so later scans stop raising it. Otherwise, replace the four strings before the first push.

[NOTE] pyproject.toml:13, requirements.txt:4-8, install.sh:27-28. Dependencies use lower bounds only, with no lock file or hashes. Re-checked; unchanged since the prior scan.
  Attack vector: `install.sh` upgrades pip and installs the newest numpy release from PyPI on every install. A compromised future release would therefore put unreviewed code into an app that keys a transmitter. Installed: numpy 2.5.4 and pip 26.2.1 in the venv, and pyserial 3.5 from apt. These versions were not checked against a vulnerability database. The package names are correct (`pyserial`, not the unrelated `serial`).
  Remediation: Ship a constraints file with hashes (for example, `pip install --require-hashes -c constraints.txt -e .`) or pin known-good versions, and run `pip-audit` before releases.

[NOTE] CLAUDE.md:47. The visual-review command writes screenshots to the fixed, shared path `/tmp/shots`, and the agent then reads them back. Re-checked; the line moved from 45 to 47. Confidence: low. The attack needs a second local account. This host has one (`peter`, UID 1000), and `/tmp/shots` does not exist now.
  Attack vector: On a multi-user host, another account pre-creates `/tmp/shots` as a world-writable directory it owns. `screenshots.run` accepts the existing directory (kx3rig/screenshots.py:41 uses `os.makedirs(..., exist_ok=True)`) and writes the PNGs there. Because the other account owns the directory, it can replace the files before the agent reads them. That feeds attacker-chosen images, including embedded text instructions, to a coding agent that has shell access.
  Remediation: In the documented command, use a private directory such as `"$(mktemp -d)"` or the session scratchpad.

### Coverage

All eight dimensions were reviewed. Every tracked source, script, packaging, and documentation file at HEAD was read in full. All six screenshots, the only version of each anywhere in `main`'s history, were inspected visually and checked for PNG metadata chunks and trailing data (none present).

Runtime checks were run against the pure modules, with no hardware and no GTK:
- `Settings()` has an empty callsign and grid and the Technician class.
- An unknown class falls back to Technician, and a NaN power ceiling falls back to the default.
- `cat.is_allowed` rejects `TX;`, `PS0;`, and `SWT16;`.
- `main(["--screenshot", DIR])` exits with status 2 before the application is constructed.

Code paths traced:
- The only two calls that assert RTS (kx3rig/controller.py:247 and 306) run only after `voice_check()` or `Ft8Engine.check_tx()`.
- GApplication exports the app's actions on the user's session bus. None of them keys the transmitter.

Not fully reviewed:
- Third-party binaries and system packages: WSJT-X `jt9` and `ft8code`, `wpctl`, `timedatectl`, GTK, libadwaita, GStreamer, PyGObject, and apt's pyserial were trusted as installed. `jt9` demodulates arbitrary over-the-air signals and remains the main remote attack surface. It runs with the user's privileges.
- Dependency CVE status was not checked against a vulnerability database (pip-audit is not installed, and no online lookup was made).
- Hardware behavior was not verified: whether the cp210x driver pulses RTS when the port opens, and whether RTS drops on abnormal exit. docs/references.md:66 and 153-154 list these as open. They are safety questions rather than security ones.
- The `pre-scrub` branch was searched only for the scrubbed values. Its code was not re-audited, since it is not meant to be published.
- The test suite was not run in this pass.
- Markup-parsing widgets (toasts, Adw rows, status pages):
  - Remote input: decoded FT8 text reaches only plain-text labels and tooltips. The contact callsign and grid reach toasts and rows only after `CALL_RE`, `GRID_RE`, and `strip("<>")`, which leave A-Z, 0-9, and `/`.
  - Local input: serial replies, GStreamer errors, and same-user `/proc` command names also reach these widgets. None of them crosses a privilege boundary.

Git history checked for secrets: no credential-handling files are in scope. All eight commits on `main` were searched with `git grep` for credential patterns, email addresses, phone numbers, IP addresses, the scrubbed callsign and grid (including partial forms), and device serial numbers. Apart from the author attribution above, nothing was found, and no file has ever been deleted on `main`. The CP2102N name in tests/test_devices.py:10 carries a 4-character serial that looks like a placeholder. It could not be compared with the hardware, because no Digirig is attached. The seven commits that exist only on `pre-scrub` hold the values described in the WARN.

Post-fix pass (cycle 2): kx3rig/controller.py, kx3rig/fakeradio.py, and tests/test_station.py were read in full. For context, this pass also traced the IF parse and dispatch path (cat.py:310-332, radio.py:404-419), every key-down call site, and how the FT8 engine and window handle link events. With no serial device attached, tests/test_station.py and tests/test_cat.py were run (59 passed). On the emulator, all eight SPLIT, XIT, and transmit combinations in its IF frame parsed to the intended flags, and the reconnect window was reproduced. The SPLIT and XIT offsets were checked against the documented format only (docs/references.md:36). The KX3's IF reply and its transmit frequency under SPLIT and XIT were not confirmed on the radio: no hardware is attached and no local copy of the manuals exists. The three files were also scanned for credentials and personal data. Only the conventional `N0CALL` placeholder was found (tests/test_station.py:28). Git history checked for secrets in this pass: no credential-handling files in scope.
