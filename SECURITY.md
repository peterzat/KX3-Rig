[NOTE] kx3rig/wspr/engine.py:58, 323-325, and 358-368 (re-checked, still present). Sharing spots on WSPRnet trusts the network path. The upload is plain HTTP (line 58, as WSJT-X does), so anyone on the path can read or alter the callsign, 4-character grid, and spots it carries. WSPRnet publishes all of these anyway. `urlopen` follows 301, 302, and 303 replies and turns the POST into a body-less GET of any http, https, or ftp URL, up to 10 hops (CPython 3.14's `HTTPRedirectHandler.redirect_request`, urllib/request.py:621-653, read this session). `.read()` takes the whole reply with no size limit. The 0 to 20 s spread delay (line 359) is not followed by a fresh check of the setting, so turning Share Spots off does not stop a batch already waiting. d664373 changed only which dial is passed in (lines 310 and 324). Sharing is off by default and never runs in demo mode (line 323). Confidence: high on the code behavior; low on impact.
  Attack vector: An on-path attacker (public Wi-Fi, a hostile hotspot) while sharing is on. (1) Answer each upload with a redirect to a LAN or tailnet address: the laptop sends a blind GET there, a CSRF-style request against any service that acts on GET. (2) Answer with an endless body: memory grows until the app is killed. Separately, with no attacker: the operator turns sharing off and one more batch still goes out within 20 s.
  Evidence: `UPLOAD_URL = "http://wsprnet.org/post/"` (line 58); `urllib.request.urlopen(req, timeout=15).read()` (line 365), after `time.sleep(random.uniform(0, 20))` (line 359) with no re-check.
  Remediation: Build the opener with a redirect handler whose `redirect_request` returns None, read at most a few kilobytes of the reply, and re-check `settings.wspr_upload` and the demo flag just before each POST. Use HTTPS if wsprnet.org accepts uploads over it (not checked here; that needs a network request).

[NOTE] kx3rig/smartscan/engine.py:59, 109, 223-233, and 303; kx3rig/audio.py:125 and 168 (outside this scope, carried from the 2026-10-11 scan, not re-checked). Smartscan's audio buffer is bounded by wall-clock timestamps alone. `_feed` evicts a chunk only when it starts more than KEEP_AUDIO_S (10.5 s) before the newest one. The deque has no `maxlen`, and the timestamps are `time.time()`. After a backward clock step, nothing is evicted until the clock catches up. Until then the buffer grows by 48 KB per second of audio, `_audio_since` scans all of it on every 50 ms tick on the main loop, and each listen window includes audio from before the step. Nothing transmits, because every transmit path refuses while Smartscan sweeps. Confidence: high on the behavior (reproduced in an earlier 2026-10-12 scan); low that a large backward step happens during a sweep.
  Attack vector: No adversary in the usual case. While Smartscan sweeps, the operator sets a wrong clock back for FT8 timing, or time sync steps it back. A one-hour step holds about 170 MB until the clock catches up. Someone able to forge time-sync replies could choose the size of the step.
  Remediation: Keep a hard cap as a backstop (a `maxlen` or a running sample count), and clear the buffer when a chunk starts earlier than the newest one it holds.
