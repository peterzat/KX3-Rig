## Security Review: 2026-10-10 (scope: full)

**Summary:** First full audit, run before the initial push to the public GitHub repository. No secrets and no remote injection paths were found: over-the-air FT8 text is constrained by the message parser, reaches `jt9` and `ft8code` only as argument lists, is length-prefixed in ADIF, and reaches markup-parsing widgets only as a callsign with no markup-active characters. A post-fix re-check of the files /codefix changed found three findings resolved: the shipped default station identity (callsign and grid now default to empty, so transmit is refused until the operator sets a callsign), the `--screenshot` mode running against real hardware (now rejected without `--demo` in `main()` and again in `screenshots.run`), and the unused `TX;` allow-list entry (removed). The personal-data WARN stays open for the operator's decision, and the license-class part of the default-identity finding remains as a NOTE.

### Findings

[WARN] tests/test_config.py:27 and 29, tests/test_ft8_engine_parts.py, tests/test_ft8_messages.py, tests/test_ft8_sequencer.py, docs/screenshots/ft8-contact.png, docs/screenshots/ft8-light.png, and all five unpushed commits. Personal data in tests, screenshots, and history will be published by the first push. Requires the operator's decision; not a /codefix item.
  Attack vector: `origin` is the public repository github.com/peterzat/KX3-Rig (visibility PUBLIC) and has no refs yet (`git ls-remote origin` still returns nothing), so the first `git push` publishes all five local commits. The station callsign resolves to the licensee's name and mailing address through the public FCC ULS database. The 6-character grid locates the station to an area of roughly 6 km by 5 km, and both FT8 screenshots show the callsign plus a distance and bearing computed from that grid. Every local commit contains both values, so removing them from the working tree does not keep them out of the published history.
  Evidence: The /codefix default change removed both values from kx3rig/config.py in the working tree; they remain in config.py at HEAD. The callsign appears on 60 lines across four test files: test_config.py 2 (lines 27 and 29), test_ft8_engine_parts.py 11, test_ft8_messages.py 15, and test_ft8_sequencer.py 32 (the new engine test adds lines 156, 158, 163, and 167). The 6-character grid appears on tests/test_ft8_engine_parts.py:96 and 103. Both screenshots render the callsign in decoded and transmitted messages (not re-checked in the post-fix pass). The author's full name appears as attribution in pyproject.toml:11, kx3rig/app.py:165 and 171, and data/com.zatloukal.KX3Rig.metainfo.xml:9. CODEREVIEW.md, written by this /codereview run and not yet tracked, quotes the callsign on 3 lines and the 6-character grid on line 30, so committing it as is would publish both again.
  Remediation: Decide before the first push. If publishing the callsign and name is intended (callsigns are public identifiers and the name is deliberate attribution), record it under Accepted Risks, and consider trimming the grid to 4 characters. Otherwise, replace the callsign in tests with a placeholder in the style the tests already use (K1ABC, W1AW), drop the 6-character grid from tests, regenerate the FT8 screenshots in demo mode with `XDG_CONFIG_HOME` pointing at a scratch settings.json that holds a placeholder callsign, redact both values from CODEREVIEW.md before it is committed, and rewrite the five unpushed commits. The empty defaults this remediation originally depended on are now in place.

[NOTE] kx3rig/config.py:32 and 56-57. The license class still defaults to General, and `clamp()` replaces any unrecognized class with General, so the license-privilege check is permissive until the operator changes it. This is the part of the resolved default-identity WARN that the fix did not cover. Confidence: medium that it matters in practice, because the callsign gate now sends every new operator to Preferences, where the License Class row sits directly below Callsign and Grid (ui/preferences.py:53-62).
  Attack vector: No adversary; the risk is an operator transmitting outside their license through a permissive default. A Technician licensee starts without a settings file, follows the "Add your callsign in Preferences to transmit." prompt (controller.py:200-201), enters a callsign, and leaves License Class at the preselected General. `can_transmit()` passes that class to `bandplan.tx_check` (controller.py:207), which then permits FT8 at 14.074 MHz and 7.074 MHz. The repository's own TECHNICIAN table allows data only on 28.000-28.300 MHz and 50.100-54.000 MHz (bandplan.py:133 and 136); run with "Technician", `tx_check` refuses both dials ("Technician class has no data privileges on 20 m.").
  Evidence: config.py:32 sets `license_class: str = "General"`; config.py:56-57 fall back to "General"; bandplan.py:200 and 214 fall back to the GENERAL table for an unknown class; tests/test_config.py:10 and 31 pin the default and the fallback; README.md:26 documents "General by default".
  Remediation: Default and fall back to the most restrictive class (Technician) in config.py and bandplan.py, or store no class until the operator picks one and have `can_transmit()` refuse with a prompt to choose it in Preferences. This station's settings.json already stores its class explicitly, so it is unaffected. Update tests/test_config.py:10 and 31 deliberately.

[NOTE] pyproject.toml:13, requirements.txt:4-8, install.sh:27-28. Dependencies use lower bounds only, with no lock file or hashes.
  Attack vector: `install.sh` upgrades pip and installs the newest numpy release from PyPI on every install, so a compromised future release would put unreviewed code into an app that drives a transmitter. No known CVE affects the installed versions (numpy 2.5.4 in the venv, pyserial 3.5 from apt), but this was not checked against a vulnerability database. Package names are correct (`pyserial`, not the unrelated `serial`).
  Remediation: Ship a constraints file with hashes (for example, `pip install --require-hashes -c constraints.txt -e .`) or pin known-good versions, and run `pip-audit` before releases.

[NOTE] CLAUDE.md:45. The visual-review command writes screenshots to the fixed, shared path `/tmp/shots`, and the agent then reads them back. Confidence: low. This requires a second local account, and this host has only one.
  Attack vector: On a multi-user host, another account pre-creates `/tmp/shots` as a world-writable directory it owns. The app writes into it (screenshots.py:41 uses `os.makedirs(..., exist_ok=True)`), and the other account can then swap the PNGs before the agent reads them. That feeds attacker-chosen images, including embedded text instructions, to a coding agent that has shell access.
  Remediation: In the documented command, use a private directory such as `mktemp -d` or the session scratchpad.

### Coverage

All eight dimensions were reviewed across every tracked file. The six screenshots were inspected visually and for PNG metadata chunks (none present). Not fully reviewed:
- Third-party binaries and system packages: WSJT-X `jt9` and `ft8code`, `wpctl`, `timedatectl`, GTK, libadwaita, GStreamer, PyGObject, and apt's pyserial. These were trusted as installed system components. `jt9` demodulates arbitrary over-the-air signals and is the main remote attack surface; it runs with the user's privileges.
- Dependency CVE status was not checked against a vulnerability database (pip-audit is not installed, and no online lookup was made).
- Third-party callsigns in the demo traffic (kx3rig/ft8/__init__.py:27-58) and test fixtures were not checked against the FCC ULS. They carry no data beyond the callsign.
- Hardware behavior (whether RTS pulses when the port opens, and whether it drops on abnormal exit) was not verified. docs/references.md:58-60 and 146-147 list it as unverified; it is a safety question rather than a security one.
- Widgets that parse Pango markup (Adw.Toast titles, which use markup by default in the installed libadwaita 1.5.0, ActionRow subtitles, StatusPage descriptions) receive app strings, local serial, GStreamer, and OS error text, and same-user `/proc` command names. One remote input does reach them: FT8 engine events put the contact callsign into toast titles (ft8/engine.py:336 and 362, shown through ui/window.py:51 and 173). The message parser (ft8/messages.py:25) and `strip("<>")` (ft8/sequencer.py:96 and 180) limit it to A-Z, 0-9, `/`, and `.`, which carry no markup meaning, so nothing is reported. The full audit had said no remote input reached these widgets; the post-fix pass corrected that.

Post-fix re-check, in the same /codereview run: the 15 files /codefix changed were re-read in full and the new data flows traced. Microphone selection reaches GStreamer only as a `target-object` property (audio.py:202-203), not through a parsed pipeline string. Demo mode opens no serial port and no audio device, so it is a sound boundary for `--screenshot`. Verified by running code with the Application class stubbed so nothing could reach hardware: `main(["--screenshot", DIR])` exits with status 2 before the Application is constructed, `cat.is_allowed("TX;")` is False, and `Settings()` has an empty callsign and grid. The five in-scope test files pass (100 tests). No automated test covers the `--screenshot` argument check. README.md, which /codefix also changed, was outside this pass's scope.

Git history checked for secrets: there are no credential-handling files in scope. The full history of all five commits was scanned with `git log --all -p` for secrets, email addresses, phone numbers, street addresses, and device serial numbers. No file has ever been deleted from history. No commits were added before the post-fix pass, so that scan stands.
