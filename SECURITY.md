## Security Review: 2026-10-10 (scope: paths)

**Summary:** Path-scoped review at HEAD (266a725) of the seven source and test files changed since the last scan (b8090c9 and 266a725; `main` is one commit ahead of `origin/main`). The changes add no attack surface and no secrets. Two in-scope NOTEs are partially resolved again. SPLIT and XIT, a rejected frequency SET, reconnect, and a stale submode still pass, and each was reproduced in this run. Post-fix re-check (same run) of the uncommitted /codefix changes to kx3rig/bandplan.py, kx3rig/controller.py, kx3rig/ft8/engine.py, and tests/test_station.py: no new findings, and the three NOTEs in these files remain. `play_data` now marks only refusals made before key-down as retryable, and FT8 retries only those. That resolves two robustness items listed under Coverage: an audio failure after key-down now raises RTS once and stops the contact (it raised RTS 10 times), and the refusal count now resets for each contact and each transmit slot. bandplan.py is now in scope, so its `tx_check` default NOTE was re-checked rather than carried.

### Findings

[NOTE] kx3rig/radio.py:253-260, 408-413, 505-509, and 558-582; kx3rig/controller.py:218-221. Key-down can still be approved against SPLIT, XIT, or frequency state that is not the radio's current one. Re-checked in this run: partially resolved. The `ptt` gate now checks for a pending or in-flight tune before it compares frequency and mode, under the same lock (radio.py:253-260). That closes the fourth window. Three windows remain. Confidence: high that each exists (reproduced in this run); low that any occurs in normal operation. Post-fix: the fix does not touch these paths, and controller.py:218-221 is unchanged. A retried FT8 key-down re-runs `check_tx` and the `ptt` gate (verified on the emulator), so the retry adds attempts but no new window.
  Attack vector: No adversary. (1) SPLIT and XIT are read from the main-loop copy (controller.py:218), and the `ptt` gate compares only frequency and mode. A SPLIT or XIT change that the link has read but the main loop has not yet applied therefore passes. (2) A rejected frequency SET. `_get("FA;")` returns the SET's `?;` as its answer and discards the FA reply read in the same batch (radio.py:408-413). `_tuning` then clears (radio.py:564-566), and both copies hold the requested frequency until the next IF reply. (3) Reconnect. `_handshake` publishes CONNECTED (radio.py:505) before it reads IF (radio.py:506-509). An active FT8 contact now stops when the main loop sees the link down (ft8/engine.py:219-221). That removes the automatic path through this window for any outage a 100 ms tick observes. Tune, Talk, and a newly started contact remain exposed for the one IF round trip.
  Evidence: Demo emulator, General class, DATA mode. (1) The link showed SPLIT on (XIT on in a second run) while the main loop had not yet updated. `can_transmit` and `play_data` were allowed, and RTS rose. (2) The radio was on 14.230 MHz, and a tune to 14.074 MHz was rejected with `?;`. With the next IF write held, both copies showed 14.074 MHz, the check approved it, and the radio keyed on 14.230 MHz (5 of 5 runs). (3) The radio was retuned to 14.230 MHz during an outage, and the post-handshake IF write was held. The check approved 14.074 MHz, and the radio keyed on 14.230 MHz. `tx_check` refuses 14.230 MHz DATA for General. Resolved window: the calling thread was paused for 2 s just before the lock in `ptt`. A queued change to the 40 m band, or to USB, was applied during the pause, and `ptt(True, expect_frequency=14_074_000, expect_mode=DATA)` refused both. With nothing queued, the same paused call keyed.
  Remediation: In `ptt(True)`, refuse when the link's live `split` or `xit_on` is set. Keep `tuning_pending` true until an FA or IF reply read after the SET confirms the new frequency. Treat `?;` or a missing reply as unconfirmed, and match the GET's own reply rather than a `?;` left over from the SET. Read IF before publishing CONNECTED, in the same state update. Ideally, read IF just before asserting RTS.

[NOTE] kx3rig/ft8/engine.py:128-133; kx3rig/radio.py:253-260, 419-431, and 543-547. The FT8 submode check can pass on a stale submode. Re-checked in this run: partially resolved. An unknown submode now refuses ("Waiting for the radio's data submode."), and so does an unknown power setting (controller.py:212-214). Both were verified on the emulator. The stale case remains. The link reads DT only every fifth poll cycle in a data mode (radio.py:543-547), not when an IF reply shows a change into DATA (radio.py:419-431), and the `ptt` gate does not compare the submode. Confidence: high on the code behavior (reproduced). Low on the on-air effect, because the sourced references do not describe the sideband and signal source of the other submodes. Post-fix: unchanged. The unknown-submode and unknown-power refusals now have tests (tests/test_station.py:340-355).
  Attack vector: No adversary. An operator who changes the submode on the front panel and starts FT8 or Tune within about a second passes the check on the old value.
  Evidence: After the emulator's submode was changed to AFSK A, `check_tx` and `play_data` were allowed at once, and RTS rose. The link saw AFSK A 0.61 s later.
  Remediation: Read DT whenever an IF reply changes the mode into DATA. Include the submode in the `ptt` gate for data transmissions, for example as an `expect_submode` argument compared with the link's live value.

[NOTE] install.sh:27-28, constraints.txt:1-8, pyproject.toml:2. Install-time code is still fetched unpinned (carried from the 2026-10-10 scan, not re-checked). numpy and pyserial resolve to the versions in constraints.txt. install.sh:27 upgrades pip with no version. The `setuptools>=64` build backend is installed into pip's isolated build environment, where `-c` does not apply. The pins carry no hashes. Confidence: high that pip and setuptools are unpinned; exploitation needs a compromised release.
  Attack vector: A compromised future release of pip or setuptools on PyPI runs with the user's privileges during `./install.sh`, building the venv of an app that keys a transmitter.
  Remediation: Pin pip (for example `pip install 'pip==26.2.1'`) or drop the upgrade. Add a tested `setuptools==` pin to constraints.txt and pass `--build-constraint constraints.txt`. Consider hashed pins with `--require-hashes`, and run `pip-audit` before releases.

[NOTE] kx3rig/bandplan.py:187 and 213. `tx_check` and `privilege_segments` still default `license_class` to "General". Re-checked in the post-fix pass: still present. Confidence: high that no current caller omits it. The only app caller of `tx_check`, `Station.can_transmit` (controller.py:221), passes `settings.license_class`, which defaults to Technician and is reset to Technician when unknown (config.py:35 and 67-68). `privilege_segments` has no app caller; only tests/test_bandplan.py:89 calls it.
  Attack vector: No adversary; the gap is latent. A future transmit path that called `tx_check(dial, mode)` would approve General segments for a Technician operator.
  Remediation: Make `license_class` a required parameter in both functions, or default it to "Technician".

[NOTE] HEAD tree, location withheld (outside this run's scope). One line still contains the 4-character prefix of the grid locator that the history scrub removed. The scrub replaced that prefix in the tests, where it was paired with the scrubbed callsign. This line pairs it with a different callsign, so it does not identify the operator by itself. The file and line are not recorded here because this repository is public, and naming them would tie the value to the operator. They were given in this run's session output. Confidence: high that the value matches (a whole-word match against the value the scrub removed). Low that it matters, because a 4-character locator spans 1 degree of latitude by 2 degrees of longitude.
  Attack vector: A reader of the public repository learns the operator's region only if something ties this locator to the operator. Nothing in the tree does; a precise citation in a committed file would.
  Remediation: Replace the locator in that line with one unrelated to the station, as the scrub did in the tests, or record it under Accepted Risks. Include the 4-character prefix in future identity searches. Keep the location out of SECURITY.md, CODEREVIEW.md, and commit messages.

Robustness items passed to /codereview (not security):
- `RadioLink._update` (radio.py:277-286) calls `on_state` outside `_state_lock`. A link snapshot computed before a main-thread update (the optimistic frequency in `set_frequency`, or the `ptt` flag) can therefore be queued after it. Forced with a pause, the queue order was: main thread at 14.100 MHz, then link at 14.074 MHz, then link at 14.100 MHz. The main-loop copy holds the older value until the next link snapshot. The `ptt` frequency comparison refuses in that state, so this fails closed. It first showed up as an unexpected refusal in an unforced run of the rejected-SET probe.
- FT8 now retries a refused `play_data` (ft8/engine.py:314-322). When the transmit audio fails to start, `play_data` has already keyed and then unkeys (controller.py:325-346), so each retry raises RTS once with no audio. The probe saw 10 RTS rises before the contact stopped; the previous code stopped after one. Each retry re-runs `check_tx` first.
- `_refusals` resets only after a successful `play_data` (ft8/engine.py:323), not in `halt()` or for a new contact. After one give-up, the next contact stopped on its first transient refusal, with the counter at 11. This fails closed.
- `power_set` is still polled every fifth cycle (radio.py:543-547), so a front-panel power increase above the maximum is seen late, by the same mechanism as the submode. This was not probed in this run. It is equipment safety, not license compliance.
