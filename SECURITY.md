[NOTE] kx3rig/smartscan/engine.py:59, 109, 221-231, and 301; kx3rig/audio.py:125 and 168 (outside this scope, read for context). Smartscan's audio buffer is bounded by wall-clock timestamps alone (re-checked, still present, and again in the post-fix pass). `_feed` evicts a chunk only when it starts more than KEEP_AUDIO_S (10.5 s) before the newest one, the deque has no `maxlen`, and the timestamps are `time.time()`. After a backward clock step, nothing is evicted until the clock catches up. Until then:
- The buffer grows by 48 KB per second of audio.
- `_audio_since` scans all of it on every 50 ms tick, on the main loop.
- Every listen window includes the 10.5 s recorded before the step. Each step then ends as soon as the radio reaches it, and a station heard before the step is listed again at later steps' frequencies.

A forward step of more than about 3 s during a listen window stops the sweep with "radio audio stopped", which is safe. Nothing transmits either way, because every transmit path refuses while Smartscan sweeps. Confidence: high on the behavior (reproduced); low that a large backward step happens during a sweep.
  Attack vector: No adversary in the usual case. While Smartscan sweeps, the operator sets a wrong laptop clock back for FT8 timing, or time sync steps it back. A one-hour step holds about 170 MB until the clock catches up. Someone able to forge time-sync replies could choose the size of the step. How the ThinkPad syncs its clock was not checked.
  Evidence: Re-run this session against HEAD. 20 s of 256-sample chunks kept 10.5 s. After a 600 s backward step and 300 s more audio, the buffer held 310.5 s (14,555 chunks, 14.9 MB), and a listen window opened 5 s after the step returned 15.3 s of audio. The post-fix pass re-ran it against the working tree with the same result (310.5 s, 14.9 MB, no `maxlen`). A window opened 5 s after the step and read 5 s later returned 15.5 s, of which 10.5 s predates the step.
  Remediation: Keep a hard cap as a backstop, such as a `maxlen` sized for KEEP_AUDIO_S at the smallest expected buffer, or a running sample count. Clear the buffer when a chunk starts earlier than the newest one it holds.

[NOTE] kx3rig/smartscan/engine.py:186-190, 245-256, 258-267, and 316-329; kx3rig/radio.py:516-519 and 535. A sweep step can retune the radio during a transmission keyed at the radio (re-checked, still present). Station refuses band, frequency, and mode changes while transmitting (controller.py:180-208). Smartscan instead calls `link.set_frequency` directly: at every step, at the filter re-plan (`_resize_for_filter`), and when it restores the dial on Stop. It learns of a front-panel key-down only from the next poll (about 0.2 s). The link applies queued SETs before it reads the transmit state (radio.py:517-519; the IF read is at 535). Once Smartscan sees the transmission, it stops without restoring (engine.py:265-267), so the radio stays where the step put it. Confidence: high that a SET can go out while keyed; low on the effect, because how the KX3 handles FA during transmit was not checked against a source.
  Attack vector: No adversary. While Smartscan sweeps, the operator holds XMIT (TUNE) or presses PTT on the radio. If a step boundary falls within the first poll interval, KX3-Rig sends the next step's FA SET while the radio is keyed. The 2026-10-11 scan saw this in 1 of 12 emulator trials, 0.14 s after key-down.
  Remediation: In the link, read TQ before applying queued band, frequency, and mode SETs, and refuse them while the radio reports transmit. TQ is already on the allow-list. This covers the step, re-plan, and restore paths at once.

[NOTE] kx3rig/controller.py:428-437 and 504-511; kx3rig/audio.py:305-309 (outside this scope, read for context). The clip player treats the sink name "auto" as a request for `autoaudiosink`, which has no explicit target and no `node.dont-reconnect` (re-checked, still present). The intended use is demo mode on macOS (controller.py:509), but the test is on the name. `_listen_sink` returns the default sink's node.name, so a Linux default sink named "auto" would take the unpinned path. CLAUDE.md requires every stream to set both properties, because listening audio must never reach the Digirig output. The other sink outcomes fail closed: no default sink, or only the Digirig, refuses the replay (tests/test_station.py:445-458 covers the Digirig cases). Confidence: low that a sink is named "auto".
  Attack vector: No adversary in practice. The default sink is a node named "auto". During a replay it disappears, or the Digirig becomes the default, and the clip follows the default to the Digirig output, which feeds the KX3's microphone input.
  Remediation: Pass the platform default as a separate argument, used only on macOS in demo mode, instead of a value in the node-name namespace.

[NOTE] kx3rig/controller.py:231-233; kx3rig/radio.py:203-207, 253-260, 408-413, 507-511, and 561-585; kx3rig/smartscan/engine.py:186-190. Key-down can still be approved against SPLIT, XIT, or frequency state that is not the radio's current one (re-checked, still present). `can_transmit` reads SPLIT and XIT from the main-loop copy. The `ptt` gate compares only pending tuning, frequency, and mode. A `?;` reply to a frequency SET leaves the optimistic frequency in place until the next IF reply. The handshake publishes CONNECTED before it reads IF. Smartscan's restore SETs on Stop take the same verified-SET path. Confidence: high that each window exists; low that any occurs in normal operation.
  Attack vector: No adversary. (1) The link has read a SPLIT or XIT change that the main loop has not applied. (2) A rejected frequency SET leaves both copies on the requested frequency until the next IF reply. (3) Reconnect publishes CONNECTED before it reads IF.
  Remediation: Refuse `ptt(True)` when the link's live `split` or `xit_on` is set. Keep `tuning_pending` true until a reply read after the SET confirms the frequency. Read IF before publishing CONNECTED.

[NOTE] kx3rig/radio.py:253-260, 419-431, and 546-550; kx3rig/ft8/engine.py:128-133 (outside this scope). The FT8 submode check can pass on a stale submode. The ft8/engine.py part is carried from the 2026-10-10 scan, not re-checked. An unknown submode refuses, but a stale known value passes until the next DT poll, about a second in a data mode. Confidence: high on the code behavior; low on the on-air effect.
  Attack vector: No adversary. The operator changes the submode on the radio and starts FT8 or Tune within about a second.
  Remediation: Read DT whenever an IF reply changes the mode into DATA, and compare the submode in the `ptt` gate for data transmissions.

- Clips. Both keying paths stop a playing clip before RTS goes up (controller.py:250 and 339). A key-down at the radio stops it at the next state update (controller.py:153-154). `play_clip` refuses while transmitting (controller.py:502-503), and the replay buttons go insensitive while keyed (ui/smartscan.py:232-234 and 361-365). Halt (Esc) does not stop a clip, which is safe because any key-down stops it. Clips live in memory only: nothing in smartscan/, looptune/, or controller.py writes audio to disk.
- Loop Tune. `LoopTuneDialog` is built only at ui/window.py:199, behind `open_refusal` (looptune/tuner.py:81-89), which refuses while transmitting or while the FT8 engine is busy. An idle FT8 sequencer ignores decodes (ft8/sequencer.py:169-172, read for context), so the engine cannot start keying on its own once the guide is open. tuner.py makes no `ptt` or `play_data` call. `demo_hold_tune` reaches only the emulator, because `Station._fake` exists only in demo mode (controller.py:95-98).

The network path passes only `grid4(settings.grid)` to conditions.py. Demo mode returns before any fetch (engine.py:404-410), and a test asserts it.
- Output handling. Smartscan text reaches plain Gtk.Label text and tooltips. The markup-parsing widgets in scope (Adw.Toast titles, Adw.ActionRow titles and subtitles, Adw.Banner) receive app-built text, numbers, local error text (GStreamer, serial), and FT8 callsigns. FT8 callsigns are limited to A-Z, 0-9, and "/" before they reach the engine's toasts (ft8/messages.py:25, ft8/sequencer.py:93-96 and 176-180), so over-the-air text cannot inject markup. The garbled-reply toast (radio.py:484, ui/window.py:205-206) stays unreported, as in earlier scans: only a device on the operator's own USB serial port controls that text, and such a device could inject keystrokes outright.
- PII. The 6-character locators in scope, at HEAD and in the rewritten branch history, are the published square's center and a corner subsquare, and W1AW's published locator. The coordinates are city-level (one decimal place). Callsign-shaped tokens are placeholders (N0CALL and "AAA" or "BBB" suffixes), a demo prefix, and W1AW. This Mac has no KX3-Rig settings file or WSJT-X configuration, so no exact-value search for the operator's callsign or locator was run.
