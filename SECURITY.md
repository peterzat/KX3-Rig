[NOTE] kx3rig/smartscan/engine.py:59, 108, and 221-231; kx3rig/audio.py:124-125 (outside this scope, read for context). New in the post-fix re-check. Smartscan's audio buffer is now bounded by timestamps alone, and they are wall-clock times. /codefix dropped the deque's 2000-chunk `maxlen`. `_feed` now evicts a chunk only when it starts more than KEEP_AUDIO_S (10.5 s) before the newest one, and `end_time` is `time.time()` (audio.py:125). After a backward clock step, the chunks recorded before it look newer than every new one, so nothing is evicted until the clock catches up. Until then:
- The buffer grows by 48 KB per second of audio.
- `_audio_since` scans the whole buffer on every 50 ms tick, on the main loop.
- Every listen window includes the 10.5 s recorded before the step. Each step then ends as soon as the radio reaches it, and its detections and clip come partly from that stale audio, so a station heard before the step is listed again at later steps' frequencies.

A forward step of more than about 4 s during a listen window at most stops the sweep, with "radio audio stopped". Nothing transmits, because every transmit path refuses while Smartscan sweeps. Confidence: high on the behavior (reproduced); low that a large backward step happens while Smartscan is on.
  Attack vector: No adversary in the usual case. While Smartscan sweeps, the operator sets a wrong laptop clock back for FT8 timing, or time sync steps it back. A one-hour step holds about 170 MB until the clock catches up. Someone able to forge time-sync replies could choose the size of the step. How this ThinkPad syncs its clock, and whether it steps backward, was not checked.
  Evidence: Calling `_feed` directly with 256-sample chunks, 20 s of audio kept 10.5 s. After a 600 s backward step, 300 s more audio kept 310.5 s (14,555 chunks, 14.9 MB), and `_audio_since` for a window opened after the step returned the 10.5 s from before it. The old 2000-chunk cap limited both effects to about 43 s.
  Remediation: Keep a hard cap as a backstop, such as a `maxlen` sized for KEEP_AUDIO_S at the smallest expected buffer, or a running sample count. Clear the buffer when a chunk starts earlier than the newest one it holds.

[NOTE] kx3rig/smartscan/engine.py:245-256, 258-267, and 316-329; kx3rig/radio.py:516-519. A sweep step can retune the radio during a transmission keyed at the radio. Station refuses band, frequency, and mode changes while transmitting (controller.py:180-208). Smartscan calls `link.set_frequency` directly at every step, and it learns of a front-panel key-down only from the next poll (about 0.2 s). The re-plan for the scan mode's filter that /codefix added (`_resize_for_filter`) is one more such step, behind the same transmit check (engine.py:265-267). The link sends queued SETs before it reads the transmit state (radio.py:518-519, re-checked post-fix). Once Smartscan sees the transmission it stops without restoring (engine.py:265-267), so the radio stays where the step put it. Confidence: high that a SET can go out while keyed; low on the effect, because how the KX3 handles FA during transmit was not checked against a source.
  Attack vector: No adversary. While Smartscan sweeps, the operator holds XMIT (TUNE) or presses PTT on the radio to answer a station. If a step boundary falls within the first poll interval, KX3-Rig sends the next step's FA SET while the radio is keyed.

[NOTE] kx3rig/smartscan/conditions.py:118 and 164-167; kx3rig/ft8/grid.py:14-17 (outside this scope, read for context); kx3rig/smartscan/engine.py:429-435 and 444-452. One malformed sender locator in PSKReporter's reply blanks the band outlook. `parse_pskreporter` keeps `senderLocator` as received, and `grade` passes it to `maidenhead.distance_km`. `to_latlon` tests `isdigit()` and then calls `int()`; for a superscript digit, `isdigit()` is true and `int()` raises ValueError. The worker catches it, so nothing crashes, but the whole fetch is discarded. The panel then shows "Couldn't reach PSKReporter" when no earlier outlook exists, or silently keeps the old one. Confidence: high on the code behavior (reproduced); low on reachability, because whether PSKReporter stores and returns such a locator was not checked.
  Attack vector: PSKReporter's reports come from whatever reporting software sends them, and a sender can claim any receiver locator (not verified this session). One report with a malformed sender locator, from a receiver claiming the operator's square, would blank the outlook for every KX3-Rig user who queries that square, for the 15 minutes it stays in the window.
  Evidence: With one valid report and one whose sender locator was "AA²²", `grade` raised `ValueError: invalid literal for int() with base 10: '²'`. "AA①②" and "AA²²xx" did the same.
  Remediation: Validate locators against an ASCII pattern (`[A-R]{2}[0-9]{2}([a-x]{2})?`, case-insensitive) before computing distance, and skip a report that fails instead of failing the outlook. In grid.py, check `isascii()` as well as `isdigit()`, the fix already applied in cat.py.

[NOTE] kx3rig/audio.py:305-306; kx3rig/controller.py:428-437 and 504-511. The clip player treats the sink name "auto" as a request for `autoaudiosink`, which has no explicit target and no `node.dont-reconnect`. The intended use is demo mode on macOS, but the test is on the name. On Linux, a default sink whose node.name is "auto" (for example a virtual sink named that way) also takes the unpinned path, and the stream can then follow the default if it changes during playback. CLAUDE.md requires every stream to set both properties, because listening audio must never reach the Digirig output (audio.py:12-15). Confidence: low that this occurs.
  Attack vector: No adversary in practice. The default sink is a node named "auto". During a replay it disappears, or the Digirig becomes the default, and the clip follows the default to the Digirig output, which feeds the KX3's microphone input.
  Remediation: Pass the platform default as a separate argument, used only on macOS in demo mode, instead of a value in the node-name namespace.
