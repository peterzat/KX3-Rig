### Findings

[NOTE] kx3rig/radio.py:248-259, 407-412, 504-508, and 557-581; kx3rig/controller.py:216-218 and 258. Key-down can still be approved against SPLIT, XIT, frequency, or mode state that is not the radio's current one. Re-checked in this run: partially resolved. The new `expect_frequency`/`expect_mode` gate in `ptt` closes the reported case: this run repeated the prior probe (a tune to 14.230 MHz applied by the link while the main-loop update was still queued), and `play_data` was refused. The post-fix tests now cover that case (tests/test_station.py:160-173). Four windows remain; the post-fix re-check added the fourth. Confidence: high that each exists (this run reproduced all four, the fourth with a forced pause); low that any occurs in normal operation.
  Attack vector: No adversary. (1) SPLIT and XIT are still read from the main-loop copy (controller.py:216), and the gate compares only frequency and mode. A SPLIT or XIT change made on the radio therefore passes while its idle update is queued. Before that, it is invisible to both copies until the next IF poll. (2) A rejected frequency SET. `_get("FA;")` accepts the SET's `?;` as its answer and discards an FA reply read in the same batch (radio.py:407-412). `_tuning` then clears (radio.py:557-565), and both copies hold the optimistic frequency until the next IF reply. (3) Reconnect. `_handshake` publishes CONNECTED (radio.py:504) before it reads IF (radio.py:505-508), so both copies hold the pre-outage frequency. A link drop does not halt an FT8 contact between transmissions (ui/window.py:175-179), so the contact's next transmit tick can land in this window. (4) Check order in `ptt`. The frequency and mode comparisons (radio.py:248-251) run before, and outside, the `_pending_lock` block that checks for a pending tune (radio.py:256-259). A band or mode change that is still being applied at the comparisons, and finishes before the lock is taken, passes both. Only the main thread queues tuning changes, and `play_data` checks `tuning_pending` on that thread just before `ptt` (controller.py:321-323), so FT8 and Tune are not exposed. Voice is: `start_talking` calls `ptt` with no prior pending check (controller.py:258), so a band or mode change selected just before Talk can still be in flight. The main thread must then be descheduled inside those few bytecodes for the link's remaining readback round trips.
  Evidence: Demo emulator, General class, DATA mode. (1) The link showed SPLIT on (and, in a second run, XIT on) with the idle update queued. `can_transmit` and `play_data` were allowed, and the radio keyed with SPLIT (XIT) on. (2) The radio was on 14.230 MHz, and a tune to 14.074 MHz was rejected with `?;`. With the next IF write held, the check approved 14.074 MHz and the radio keyed on 14.230 MHz. (3) The radio was retuned to 14.230 MHz during an outage, and the post-handshake IF write was held. The check approved 14.074 MHz and the radio keyed on 14.230 MHz. The transmission continued after the IF reply corrected the frequency. `tx_check` refuses 14.230 MHz DATA for General. (4) Post-fix probe: `sys.settrace` paused the calling thread for 2 s at radio.py:256. With a change to the 40 m band queued, `ptt(True, expect_frequency=14_074_000, expect_mode=DATA)` keyed the radio on 7.185 MHz LSB; with a change to USB queued, it keyed in USB. Without the pause, both were refused.
  Remediation: In `ptt(True)`, refuse when the link's live `split` or `xit_on` is set. Keep `tuning_pending` true until an FA or IF reply read after the SET confirms the new frequency; treat `?;` or a missing reply as unconfirmed, and match the GET's own reply rather than a `?;` left over from the SET. Read IF before publishing CONNECTED, in the same state update. Move the frequency and mode comparisons inside the `_pending_lock` block, after the pending check: `_tuning` clears only after the readback has updated the state, so the comparison then sees the applied change. Ideally, read IF just before asserting RTS.

[NOTE] kx3rig/ft8/engine.py:125-128; kx3rig/radio.py:418-430 and 543. The new FT8 submode check passes when the submode is unknown, and the value it reads can be stale. Re-checked in this run: resolved for a known non-DATA-A submode (tests/test_station.py:108-121), still present for the unknown and stale cases. The post-fix change does not touch either case. Confidence: high on the code behavior (verified); low on the on-air effect, as before, and low that the radio leaves the submode unknown in DATA mode, because the sourced references do not say how the KX3 answers DT outside DATA mode.
  Attack vector: No adversary. `sub is not None and sub is not DataSubmode.DATA_A` lets `None` through. The submode is `None` from startup until the first DT reply, and it stays `None` if the radio never answers DT. The link reads DT only every fifth poll cycle in a data mode (radio.py:543), not when an IF reply shows the mode changing to DATA (radio.py:418-430), and `ptt` does not check it. An operator who changes the mode or submode on the front panel and starts FT8 or Tune within about a second passes the check on old or missing data.
  Evidence: With `data_submode` set to `None` in `Station.radio`, `check_tx` was allowed. After the emulator's submode was set to AFSK A (a front-panel change), `check_tx` and `play_data` were allowed at once, and the radio keyed in AFSK A. The link saw AFSK A 0.61 s later.
  Remediation: Refuse unless `sub is DataSubmode.DATA_A`, as the prior remediation proposed. Read DT whenever an IF reply changes the mode to DATA, and include the submode in the `ptt` gate for data transmissions. If the check starts refusing an unknown submode, show Tune Radio to FT8 in that case too. The post-fix condition (ui/ft8_page.py:392-393) shows it only for a known submode other than DATA A, so the refusal would again point at a hidden button.

[NOTE] install.sh:27-28, constraints.txt:1-8, pyproject.toml:2. Install-time code is still fetched unpinned. Re-checked in this run: partially resolved. numpy and pyserial now resolve to the versions in constraints.txt. Two pieces of code still run at their newest PyPI versions on every install. install.sh:27 upgrades pip with no version. `pip install -c constraints.txt -e .` also installs the `setuptools>=64` build backend into an isolated build environment, where `-c` does not apply: pip 26.2.1 applies only `--build-constraint` there (pip/_internal/build_env/installer.py:130-136 in the venv). The pins also carry no hashes, so they would accept new files added to an existing release. Confidence: high that pip and setuptools are unpinned (verified in pip's source); exploitation needs a compromised release.
  Attack vector: A compromised future release of pip or setuptools on PyPI runs with the user's privileges during `./install.sh`, building the venv of an app that keys a transmitter.
  Remediation: Pin pip (for example `pip install 'pip==26.2.1'`) or drop the upgrade. Add a tested `setuptools==` pin to constraints.txt and pass `--build-constraint constraints.txt`. Consider hashed pins with `--require-hashes`, and run `pip-audit` before releases.

[NOTE] kx3rig/bandplan.py:186 and 212. `tx_check` and `privilege_segments` still default `license_class` to "General" (carried from the 2026-10-10 scan, not re-checked). Confidence: high that no current caller omits it; the only app caller, `Station.can_transmit` (controller.py:219), still passes `settings.license_class`.
  Attack vector: No adversary; the gap is latent. A future transmit path that called `tx_check(dial, mode)` would approve General segments for a Technician operator.
  Remediation: Make `license_class` a required parameter in both functions, or default it to "Technician".

### Coverage

All eight dimensions were reviewed for the 12 in-scope files. Each was read in full at HEAD, along with its diff against e6f15d3. docs/live-test.md also changed in c3b5699 but was not in the scope list, so it was not reviewed.

Runtime checks used the demo emulator only, with no serial device attached:
- The full suite passes (201 tests).
- The key-down, rejected-readback, reconnect, and submode probes described in the findings.
- An unexpected `RuntimeError` in the link during a data transmission now ends it: `on_done(False)` ran once, and PTT and RTS were off. This resolves the CODEREVIEW.md NOTE about the generic error path.
- `cat.parse_if` and `cat.parse_om` reject non-ASCII digits. No `isdigit()` followed by `int()` remains on serial input. ft8/grid.py:14 still pairs them, but its inputs are the operator's own grid and FT8-decoded grids, not serial data.
- CLAUDE.md:47 now writes screenshots to a fresh `mktemp -d` directory (mode 0700), and kx3rig/screenshots.py:31 prints each PNG path, so the agent reads the files it just wrote. The prior `/tmp/shots` NOTE is resolved.

Robustness items passed to /codereview (not security):
- A settings file with deeply nested JSON raises `RecursionError`, which `config.load()` does not catch, so the app does not start. This fails closed and needs a hand-edited file.
- When an exception repeats on every attempt, the link retries with no delay. On the emulator this produced about 43,000 "lost" events per second for `RuntimeError` (newly emitted by this commit) and about 46,000 for `OSError` (existing behavior). "lost" is not toasted (ui/window.py:175-179), so the cost is CPU time and main-loop idle callbacks. Resolved by the post-fix change (see below).
- The new power-ceiling check passes while the radio's power is unknown (`power_set` is `None` before the first PC reply). This is equipment safety, not license compliance.
- The `.bad` copy gets the process umask (0644 here) rather than the source's mode, which matches what `config.save()` already writes. The file holds only the station's on-air identity, so this is not a finding.

Code traced outside scope, for context:
- ui/window.py:171-179 and ui/ft8_page.py:388-405: a link drop updates labels but does not halt an FT8 contact.
- audio.py, devices.py, and ft8/encode.py run no nested main-loop iteration, so `ptt` reads the same `Station.radio` that the license check read.
- pip 26.2.1's handling of constraints in isolated builds (build_env/installer.py, cli/req_command.py).

Not fully reviewed:
- KX3 behavior that the sourced references do not cover was not verified, because no hardware is attached:
  - how the radio answers DT outside DATA mode;
  - whether a rejected FA SET always leaves the radio on its previous frequency, as the emulator assumes;
  - the sideband and signal source of AFSK A, FSK D, and PSK D.
- Files outside this run's scope keep their carried findings.

Post-fix re-check (same run), uncommitted /codefix changes on top of c3b5699:
- Scope: kx3rig/radio.py, kx3rig/ui/ft8_page.py, and tests/test_station.py, each read in full along with its diff. All eight dimensions were reviewed for the three files. ui/ft8_page.py was not in the earlier scope, so this was its first full review.
- Tests: 205 passed with the WSJT-X tools on PATH. With only the venv on PATH, 198 passed and 7 skipped (the WSJT-X round trips), so the CODEREVIEW.md failure without WSJT-X is gone. Both engine tests set `XDG_DATA_HOME` to `tmp_path` before building the engine, and `config.data_dir()` reads it at call time, so the jt9 work directory and the demo log stay out of the user's data directory. Demo mode never opens a real port (controller.py:89-95), so the new tests that key RTS touch only the emulator.
- Retry backoff, measured on the emulator: a `read` that always raises produced 3 "lost" events in 4.5 s, 1.5 s apart, for both `RuntimeError` and `OSError`. `stop()` returned at once during the error sleep. When the link failed while keyed, RTS dropped and never rose again, `ptt(True)` was refused during the outage, and the link reconnected once the fault cleared. Every `ptt(False)` sets the link's wake event and ends the sleep early. After a "lost" event the only such call is from `_abort_data_tx`, once per data transmission (controller.py:154-157 and 356-363), so at most one retry comes early (measured: one 0.01 s gap, then 1.5 s gaps).
- Tune Radio to FT8 (ui/ft8_page.py:392-393) now appears under the same condition the engine uses to refuse (ft8/engine.py:125-128). The button only queues a retune through `go_ft8`, which refuses while transmitting (controller.py:192-197), and `_tune_to_ft8` refuses during a contact (ui/ft8_page.py:292-295).
- Pango markup: in libadwaita 1.5.0, `AdwActionRow` titles and subtitles and `AdwToast` titles parse markup by default, and the code escapes nothing. FT8 text reaches them at ui/ft8_page.py:375 and 379-381 (`entry.call`, `entry.grid`). The call matches `CALL_RE` (ft8/messages.py:25, ASCII after `upper()`) and loses its angle brackets (ft8/sequencer.py:96 and 180); the grid matches `GRID_RE`. No markup can be formed from that text. Decode rows and the conversation use plain `Gtk.Label`. The "garbled" toast (radio.py:481) embeds the serial reply, but only a device on the operator's own USB serial port controls that text, so it is not a finding.
- Key-down windows (1) to (3) depend on code the fix does not change (the radio.py diff touches only the two `except` branches in `_run`), so they were not re-probed. Window (4) was probed as described in the finding.

Git history checked for secrets: no credential-handling files are in scope. `git log -p --follow -3` of the 12 in-scope files shows only placeholder identities (K1ABC, DM79, N0CALL) and CAT command strings.
