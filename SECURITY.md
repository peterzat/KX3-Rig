[NOTE] kx3rig/wspr/engine.py:58, 323-325, and 358-368. New. Sharing spots on WSPRnet trusts the network path. The upload is plain HTTP (line 58, as WSJT-X does), so anyone on the path can read or alter the callsign, 4-character grid, and spots it carries. WSPRnet publishes all of these anyway. `urlopen` follows 301, 302, and 303 replies and turns the POST into a body-less GET of any http, https, or ftp URL (CPython's HTTPRedirectHandler, read this session, up to 10 hops). `.read()` takes the whole reply with no size limit. The 0 to 20 s spread delay (line 359) is not followed by a fresh check of the setting, so turning Share Spots off does not stop a batch already waiting. Sharing is off by default and never runs in demo mode (line 323). Confidence: high on the code behavior; low on impact.
  Attack vector: An on-path attacker (public Wi-Fi, a hostile hotspot) while sharing is on. (1) Answer each upload with a redirect to a LAN or tailnet address: the laptop sends a blind GET there, a CSRF-style request against any service that acts on GET. (2) Answer with an endless body: memory grows until the app is killed. Separately, with no attacker: the operator turns sharing off and one more batch still goes out within 20 s.
  Remediation: Build the opener with a redirect handler whose `redirect_request` returns None, read at most a few kilobytes of the reply, and re-check `settings.wspr_upload` and the demo flag just before each POST. Use HTTPS if wsprnet.org accepts uploads over it (not checked here; that needs a network request).

[NOTE] kx3rig/keyboard/engine.py:46, 191-193, 266-268, and 286; kx3rig/bandplan.py:160-161. New. Software CW gets half the segment-edge margin that real CW gets. A keyed tone is checked as CW over the offset plus or minus 50 Hz (`WIDTH_HZ[CW] = 100`), while the KX3's own CW mode is checked over the dial plus or minus 100 Hz. Both are the same shaped, keyed carrier, and the keyboard sends up to 40 WPM. Confidence: high that the margins differ; low that the 50 Hz matters, because the keyed tone's 26 dB bandwidth was not measured.
  Attack vector: No adversary. The operator sends fast CW within 100 Hz of a CW segment's lower edge (for example a Technician just above 7.025 MHz). The check passes where the same signal sent in CW mode would be refused, and the keying sidebands may reach past the edge.
  Remediation: Use one CW margin for both paths, for example a 200 Hz span for the check while the waterfall marker stays narrow, or scale the span with WPM.

[NOTE] kx3rig/smartscan/engine.py:59, 109, 223-233, and 303; kx3rig/audio.py:125 and 168 (outside this scope, carried from the 2026-10-11 scan, not re-checked). Smartscan's audio buffer is bounded by wall-clock timestamps alone (re-checked by reading; the code is unchanged apart from a two-line shift, and the reproduction was not re-run). `_feed` evicts a chunk only when it starts more than KEEP_AUDIO_S (10.5 s) before the newest one. Until then the buffer grows by 48 KB per second of audio, `_audio_since` scans all of it on every 50 ms tick on the main loop, and each listen window includes audio from before the step.
